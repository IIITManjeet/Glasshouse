# Glasshouse v2 - design

What this document is: the design for one new `GlasshouseBook` deployment and everything
that hangs off it - rooms, a factory, self-opening rounds, a maker-side bond, invite-only
commits, timelock-sealed bids - written so that an implementation agent can take one phase
at a time without making an architecture decision. Every claim about the current code cites
a file and line in the working tree at `v2` (HEAD `53201df`). Facts fetched from outside the
repo are marked *verified* with how, or *unverified* with what would verify them.

What it is not: a reason to touch v0.9.0. The Book at `0xc4ea91Fe…` has no upgrade path
(`src/book/GlasshouseBook.sol:17-19`); it keeps resolving exactly as it does today, and the
v2 subgraph keeps indexing it as the legacy room (§6.2). The router at `0x5c3baE05…` is not
redeployed at all (§2).

Companions: `README.md` "What this does not prove" (`README.md:346-372`) and "Future work"
(`README.md:410-523`), which this document is the build plan for; `docs/design/HLD.md`,
`docs/design/LLD.md`, `docs/design/subgraph-design.md` for v1.

## 1. What is being built, in one table

| Item | Where it lives | Why it needs a new contract |

Everything that needs a contract lands in **one** Book deployment, because a second
deployment of an ownerless contract is the only upgrade path there is, and each one costs a
subgraph resync, a new rounds table (§8.1) and a new set of programs.

## 2. The router question: how opcode `0x2e` finds its Book

Answered from code, and the answer is the cheapest possible one.

The Book address is **an argument of the instruction inside the maker's program**, not
state on the router. The wire format is `[address book, uint24 maxImprovementBps]`, 23 bytes
(`src/instructions/GlasshouseAuction.sol:14`), read back by `parse` at offsets 0 and 20
(`src/instructions/GlasshouseAuction.sol:41-44`) and handed to
`GlasshouseAuctionLib.applyOutcome`, which does one `STATICCALL` to
`IGlasshouseBook(book).outcome(query.maker, query.orderHash)`
(`src/lib/GlasshouseAuctionLib.sol:51`). `GlasshouseRouter` contains no Book reference at
all: its whole body is the opcode dispatch (`src/routers/GlasshouseRouter.sol:24-28`) and a
constructor that passes `(aqua, weth, owner, name, version)` to `SwapVM`
(`src/routers/GlasshouseRouter.sol:39-45`). The Ignition module says the same thing in
prose: "the Book is referenced by ADDRESS inside a maker's program, not by the router"
(`ignition/modules/Glasshouse.ts:14-16`; `DEPLOY.md:87-89`).

Consequences:

- **A factory of Books needs no router change and no router redeploy.** A room's orders
  are programs whose `0x2e` argument names that room's Book. The existing router at
  `0x5c3baE054e8b4915a13726B397b1AeA864247DBf` serves every room ever created.
- **The EIP-170 budget is untouched.** The router stays at 21,108 B with 3,468 B of
  headroom (`docs/design/LLD.md` §10); the Book "is a separate contract and does not
  compete for that budget" (`docs/design/HLD.md:577-578`). `scripts/size-check.mjs`
  reports every artifact whose name starts with `Glasshouse`
  (`scripts/size-check.mjs:56-58`), so `GlasshouseBookFactory` and the v2 Book appear in
  `npm run size` with no change to the script. The factory embeds the Book's creation code,
  so its own runtime size is roughly the Book's plus a few hundred bytes; the v2 Book is
  estimated at 10-13 KB against a 24,576 B limit. Measure, do not assume: Phase 1 ends
  with `npm run size` in the log.
- **Two ABIs are frozen.** The instruction depends on `IGlasshouseBook.outcome` returning
  the four-field `Outcome` struct (`src/interfaces/IGlasshouseBook.sol:23-28, :40`), and
  the fill record depends on `IMakerHooks.postTransferIn`'s ten-argument signature
  (`node_modules/@1inch/swap-vm/src/interfaces/IMakerHooks.sol:45-56`). The v2 Book keeps
  both byte-identical. Everything else on the Book may change.
- **One thing the rooms design must not do:** put the Book address on the router "to save
  bytes in the program". That would tie every order to one Book and turn a room into a
  router deployment, which is the 24 KB thing.

The v1 Book keeps working for v1 programs; the keeper's 300 precomputed rounds embed the
v1 Book address in their program bytes (`test/fork/GenerateRounds.t.sol:34, :66`), so v2
rounds need a regenerated table (§8.1).

## 3. The v2 Book

The v1 contract stays the reference: `open` / `commit` / `reveal` / `outcome` / `settle` /
`claimBond` / `claimForfeit` / `claimUnrevealed`, the O(1) top-2, the phase rule and the
"forfeiture needs positive evidence" rule (`src/book/GlasshouseBook.sol:269-277`) are all
carried forward unchanged in semantics. Below is only what changes.

### 3.0 Constructor

```solidity
constructor(bytes32 inviteRoot, address aqua)
```

Both immutable. No owner, no admin, no setter, as before.

- `inviteRoot`: zero means public; non-zero gates `open` and `commit` (§3.3).
- `aqua`: the Aqua the offer check reads (§3.1). Zero disables the maker-bond path; the
  factory passes the official Aqua on Base, `0x1111113CCf1426A8E30e2bfF5E005d929bF6a90a`.

### 3.1 Maker-side bond and the offer check

**The hole.** Bidders escrow at commit (`src/book/GlasshouseBook.sol:171-172`); the maker
escrows nothing, so a maker can open an auction against an order they never ship, and the
Book cannot tell that from an honest round nobody filled. The contract deliberately
refuses to forfeit a winner without positive evidence someone else filled
(`src/book/GlasshouseBook.sol:269-277`, pinned by `test/GlasshouseBook.t.sol:590-620`).
The maker bond must be held to the same standard: **no slash without positive evidence
that the offer was not there.**

**Where positive evidence comes from.** In Aqua mode a fill needs four things to be true at
the moment of the fill, and all four are readable from chain:

1. The strategy is shipped under `(maker, app = router, strategyHash = orderHash)`.
   `Aqua.ship` keys by `keccak256(strategy)` (`node_modules/@1inch/aqua/src/Aqua.sol:41`),
   and for an Aqua order that equals `router.hash(order)`
   (`node_modules/@1inch/swap-vm/src/SwapVM.sol:109-112`; asserted equal at
   `test/fork/AquaBaseFork.t.sol:188`). `rawBalances(maker, app, strategyHash, token)`
   returns `(balance, tokensCount)` (`Aqua.sol:26-28`); `tokensCount == 0` means never
   shipped, `0xff` means docked (`Aqua.sol:19, :54-61`).
2. The declared balance of the offered token is at least what the maker promised
   (`balance` above).
3. The maker's wallet actually holds it: Aqua's `pull` is a `safeTransferFrom(maker, to,
   amount)` (`Aqua.sol:63-70`), so a declared balance with an empty wallet reverts the fill.
4. The maker has approved Aqua for it (same line).

So the Book can decide "the offer was not fillable" from three `STATICCALL`s and no
trust in the maker's configuration. This is the same shape as `filledBy`: something the
Book observed, not something the maker asserted.

**What the maker declares at `open`.** Three new parameters, all emitted in
`AuctionOpened`:

| Parameter | Type | Meaning |
|---|---|---|
| `makerBond` | `uint128` | Escrowed from the maker at `open`, in `tokenIn` (same denomination as bidder bonds, so one token per auction and one `SafeERC20` path). Zero is allowed and is what a browser-opened round with no order behind it uses. |
| `offerToken` | `address` | The token the maker promises to deliver. Not necessarily either "side": Aqua strategies are two-sided and the taker chooses direction (`SwapVM.sol:135-136`). |
| `minOffer` | `uint128` | The declared depth in `offerToken`, in its own units. Bidders read it from the event and bid against it. |

Rules at `open`:

- `makerBond > 0` requires `aqua != address(0)` on this Book, else `NoEvidencePath()`.
  Signature-mode orders have no on-chain offer to inspect; a bond that can never be
  slashed is theatre, so it is refused rather than accepted and ignored.
- `makerBond > 0` requires the strategy to be shipped *now*: `rawBalances(msg.sender,
  router, orderHash, offerToken)` must report `tokensCount` in `1..0xfe` and
  `balance >= minOffer`, else `NotShipped()`. This alone closes "open against an order
  never shipped" for bonded rounds. It is safe to ship before opening: see §3.2.
- The bond is pulled with `safeTransferFrom(msg.sender, this, makerBond)`.

**The offer check, during the window.**

```solidity
function checkOffer(address maker, bytes32 orderHash) external
```

Permissionless. Allowed only while the winner's exclusive window is running:
`revealEnd < block.number <= revealEnd + exclusiveBlocks`, `best != address(0)`,
`filledBy == address(0)`, `makerBond > 0`; otherwise `OfferCheckNotOpen()`. It reads the
four facts above and, if any fails, sets `makerDefaulted = true` and emits
`MakerDefaulted(maker, orderHash, reason, observed, required)`. Once set it stays set; a
second call is a no-op that emits nothing. A passing check writes nothing.

Why in the window and nowhere else:

- Before `revealEnd` the maker may legitimately still be arranging inventory; nobody can
  fill yet (the gate reverts on `Bidding`, `src/lib/GlasshouseAuctionLib.sol:57`).
- After the window the maker may legitimately dock: the keeper docks straight after
  settle today (`scripts/keeper.ts:478-486`), and `settle` is permissionless and may
  arrive late, so a settle-time check would slash honest makers for tidying up.
- Inside the window only the winner can fill (`GlasshouseAuctionLib.sol:66`), so
  `filledBy == 0` plus an unfillable offer means exactly one thing: the maker sold
  exclusivity on something that was not there.

Why sticky: a maker who docks after a passing check and re-funds after a failing one is
gaming a thirty-second window; "caught once in the window" is the rule, stated on the
page. A maker whose wallet dips during the window because of an unrelated transfer is
also caught - keeping the offer funded for `exclusiveBlocks` is what the bond buys.

What the check cannot catch: a maker who docks in the last block of the window after the
last `checkOffer` in it. Base has no public mempool, so the winner cannot see it coming.
The winner's own fill transaction is the natural last check; a smart-account winner can
bundle `checkOffer` and `swap` atomically, an EOA cannot. Stated as a residual, not hidden.

**Disposition at `settle`.** `settle` gains nothing new to decide; it reads
`makerDefaulted` and emits it. Afterwards:

| State | Maker bond goes to | Winner bond | Unrevealed bonds |
|---|---|---|---|
| no winner (`best == 0`) | maker (`claimMakerBond` by maker) | - | maker, as today |
| winner, `!makerDefaulted` | maker | as today (`claimBond`, or `claimForfeit` on evidence) | maker |
| winner, `makerDefaulted` | **winner** (`claimMakerBond` by `best`) | returned (`claimBond`; `winnerForfeited` is necessarily false because `filledBy == 0`) | **winner** (`claimUnrevealed` still callable by the maker, but pays `best`) |

The last cell is the one judgment call: silence is still a bidder fault, but a maker who
defaulted must not profit from the round it broke. The alternative (forfeits always to the
maker) is one fewer branch; §12 lists it.

**Sizing.** `makerBond` should cover what the winner lost by winning: gas for commit,
reveal and the failed fill attempt, plus the opportunity cost of the bidder bond being
locked for the round. The site prints a rule of thumb next to the field, labelled as one;
the contract enforces only `> 0`.

### 3.2 Rounds that open themselves

**The constraint, restated from code.** A fillable round needs a real SwapVM order
shipped to Aqua for its hash. The Book cannot ship (`Aqua.ship` is `msg.sender`-keyed,
`Aqua.sol:40-52`), so no Book function can conjure a fillable round. What a Book function
*can* do is open, at the right moment, a round for an order the maker shipped earlier.

**The fact that makes a queue safe.** An order whose `postTransferIn` hook targets the
Book is **unfillable until its auction is opened.** `SwapVM._transferIn` calls the hook
with a bare external call and no `try` (`node_modules/@1inch/swap-vm/src/SwapVM.sol:298-301`),
and the Book's `postTransferIn` requires `msg.sender == a.router`
(`src/book/GlasshouseBook.sol:251`), where `a.router` is zero for an auction that was never
opened. The hook reverts `NotRouter()`, the swap reverts with it. Every keeper order
carries that hook (`test/fork/GenerateRounds.t.sol:55-60`). So a maker can ship ten orders
in one session and none of them can be taken at base price before its round opens.
(This also corrects a README sentence; §10, F-v2-1.)

**Design: a per-maker queue, opened by anyone, tipped by the maker.**

```solidity
struct QueuedRound {
    bytes32 orderHash;
    uint40  notBefore;      // earliest block openNext may open it; the maker's pacing
    uint128 tip;            // paid to whoever calls openNext, in tokenIn
    OpenParams params;      // everything open() takes, minus orderHash
}

function enqueue(QueuedRound[] calldata rounds) external;          // maker; pulls sum(makerBond + tip)
function withdrawQueued(uint256 index) external;                    // maker; refunds an unopened entry
function openNext(address maker) external;                          // anyone; pays the tip to msg.sender
function settleAndOpenNext(address maker, bytes32 orderHash) external; // convenience: the two above
```

Rules:

- `openNext` requires the maker's most recently opened queued round to be settled (or no
  queued round to be open), `block.number >= notBefore`, and the head entry to pass the
  same `open` checks including `NotShipped()` when `makerBond > 0`. It opens the round
  under `key(maker, orderHash)` exactly as if the maker had called `open`, emits
  `AuctionOpened`, then `QueuedRoundOpened(maker, orderHash, opener, tip)` and transfers
  the tip.
- A head entry that cannot open (not shipped, `AlreadyOpened`) blocks the queue. The
  maker fixes it with `withdrawQueued(head)` or by shipping. Nobody else can skip it;
  skipping would let a stranger reorder a maker's rounds.
- `enqueue` gates on membership when `inviteRoot != 0` (§3.3), like `open`.

**Why not have `settle()` open the next round.** Three reasons, each sufficient:

1. *Gas falls on the wrong party.* `claimBond` requires `settled`
   (`src/book/GlasshouseBook.sol:287`), so the person most motivated to settle is a bidder
   reclaiming a bond. An `open` is roughly five cold `SSTORE`s plus a token pull; taxing a
   bidder's `claimBond` path with the maker's next round is the wrong incentive, and a
   bidder whose settle reverts because the *maker's* next order is not shipped is worse.
2. *Pacing.* `settle` fires when the window elapses; the keeper today deliberately waits
   `KEEPER_PAUSE_BLOCKS` between rounds (`scripts/keeper.ts:263-276`). `notBefore` on the
   queue entry carries the same pacing without a process.
3. *Failure isolation.* An `open` that reverts inside `settle` would make an auction
   unsettleable, which strands every bond in it. `settle` must stay the one function that
   cannot be blocked by anything the maker controls.

So `settle` stays as it is, and `settleAndOpenNext` exists for the keeper and for a
visitor who wants the tip in one transaction. If nobody calls `openNext`, nothing opens,
which is what an idle venue should look like (`README.md:435-437`). A zero tip is legal
and is what a maker running its own keeper sets.

**Griefing.** `openNext` can only open rounds the maker enqueued and funded, only in the
maker's order, only after `notBefore`, only after the previous one settled. The worst a
stranger can do is open the next round at the earliest moment the maker allowed, and
collect the tip the maker offered for exactly that.

**What still needs the maker's process.** Shipping (§3.2 first paragraph) and docking
(`Aqua.dock` is `msg.sender`-keyed, `Aqua.sol:54`). Settled, undocked rounds stay
fillable at base price forever; the keeper docks after settle for that reason
(`scripts/keeper.ts:478-486`). With a queue, several settled rounds may be undocked at
once and each advertises the declared depth; only the maker's real wallet balance backs
them all, and a second fill against an emptied wallet reverts on `safeTransferFrom`
(`Aqua.sol:68`) - a failed taker transaction, not a maker loss. Still, the honest sentence
on the page is the README's: no contract runs by itself; what changed is that the maker's
process now runs once per batch instead of once per round.

### 3.3 Merkle-gated `commit` and `open`

One `bytes32 inviteRoot`, immutable, set by the factory at deployment. `bytes32(0)` is a
public room and is what the v2 public Book uses.

- `commit(maker, orderHash, commitment, ciphertext, bytes32[] proof)`
- `open(OpenParams p, bytes32[] proof)` and `enqueue(..., bytes32[] proof)`

When `inviteRoot != 0`, each requires
`MerkleProof.verify(proof, inviteRoot, keccak256(bytes.concat(keccak256(abi.encode(msg.sender)))))`
(OpenZeppelin `MerkleProof`, already a dependency at `@openzeppelin/contracts` 5.4.0,
`package.json:26`), else `NotMember()`. The double-hashed leaf is OpenZeppelin's
`StandardMerkleTree` convention, so the site builds trees and proofs with
`@openzeppelin/merkle-tree` and nothing is hand-rolled.

`reveal`, `revealFor`, `checkOffer`, `settle`, `openNext` and every claim stay
permissionless: none of them lets a non-member into the auction, and each one someone
must be free to call for liveness.

Why `open` is gated too: a room whose rounds anyone could open would be a public venue
with a private bidder list. A room is a membership set; members open and members bid.
Membership of the creator is the creator's job when building the tree.

Why one immutable root per Book rather than a root per auction: it matches the README's
design ("one storage slot regardless of how many friends, and the invite you send is
their proof", `README.md:484-486`), it costs nothing per auction, and changing the list
is a new room from the factory, which on Base costs cents. The per-auction alternative
is in §12.

Proof size: `log2(n)` hashes. A 64-address room is six words of calldata, which the
invite link carries.

### 3.4 Anyone-can-reveal and the timelock ciphertext

The mechanism argument is in §4; this is the contract surface.

`commit` gains `bytes ciphertext`. `open` gains `uint64 tlockRound`.

- `tlockRound == 0`: plain v1 commit-reveal for this auction; `ciphertext` must be empty.
- `tlockRound != 0`: `ciphertext.length` must equal `TLOCK_CIPHERTEXT_LEN` (160, §4.4),
  else `BadCiphertext()`. The bytes go into the `BidCommitted` event and **nowhere in
  storage**. The contract never reads them back and cannot check them; §4.5 says why that
  is enough.

```solidity
function reveal(address maker, bytes32 orderHash, uint24 bps, bytes32 salt) external;            // as v1
function revealFor(address maker, bytes32 orderHash, address bidder, uint24 bps, bytes32 salt) external;
```

`revealFor` is `reveal` with `bidder` in place of `msg.sender` in exactly two places: the
`_bids[k][bidder]` load and the commitment check
`keccak256(abi.encodePacked(bidder, bps, salt))` (v1 at
`src/book/GlasshouseBook.sol:189-192`). The top-2 update, the phase checks, the range
check and the event are identical; `reveal` becomes `revealFor(..., msg.sender, ...)`.
`BidRevealed` gains `revealedBy` so the record shows who opened whose bid.

The `tlockRound` is recorded in `AuctionOpened` only. The contract does not validate it;
the client does (§4.3), for the same reason `bid.js` range-checks a bid before `commit`
accepts it blindly (`web/lib/bid.js:923-938`): the contract cannot protect a bidder from
a bad number here, so the page must.

### 3.5 Storage layout

`Auction`, repacked as LLD G-1 recommends (`docs/design/LLD.md:935-943`), with the new
fields. Six v1 slots become eight; `outcome()` reads slots 0, 1 and 3 only.

| Slot | Fields (bytes) | Writer |
|---|---|---|
| 0 | `router` (20), `commitEnd` (5), `revealEnd` (5) | `open` |
| 1 | `tokenIn` (20), `exclusiveBlocks` (5), `reserveBps` (3), `maxBps` (3) | `open` |
| 2 | `bond` (16), `makerBond` (16) | `open` |
| 3 | `best` (20), `bestBps` (3), `bestCommitIdx` (5), `secondBps` (3) | `reveal`/`revealFor`, only while `block.number <= revealEnd` |
| 4 | `commitCount` (5), `filledBy` (20), `settled` (1), `winnerForfeited` (1), `makerDefaulted` (1), `makerBondClaimed` (1) | `commit` (count), hook, `checkOffer`, `settle`, `claimMakerBond` |
| 5 | `offerToken` (20) | `open` |
| 6 | `minOffer` (16), `queueIndex` (5, `0` = opened directly, else 1-based position in the maker's queue) | `open` / `openNext` |

`outcome()` (v1 `src/book/GlasshouseBook.sol:213-232`) is unchanged and touches nothing
written after `revealEnd`: `makerDefaulted` lives in slot 4 with the other post-freeze
flags and is never read by it. That preserves the storage-partition argument of
`docs/design/LLD.md` §2.1.1 verbatim.

`Bid` is unchanged (`commitment`, `commitIdx`, `revealed`, `bondClaimed`; two slots). The
ciphertext is not stored.

New top-level storage:

```solidity
mapping(address maker => QueuedRound[]) private _queue;
mapping(address maker => uint256)       private _queueHead;      // next index to open
mapping(address maker => bytes32)       private _queueCurrent;   // key of the last queued round opened
bytes32 public immutable inviteRoot;
address public immutable aqua;
```

`QueuedRound.params` is stored as a struct (one `SSTORE` per packed slot, about four
slots per entry). Entries are deleted when opened or withdrawn, so the array does not grow
without bound in gas terms; the head index is what moves.

### 3.6 Events

The subgraph is built on these; the signatures are frozen at the end of Phase 1 and every
later phase reads them from `subgraph/abis/GlasshouseBookV2.json`. Changes from v1 in
bold.

```solidity
event AuctionOpened(address indexed maker, bytes32 indexed orderHash, address router, address tokenIn,
    uint40 commitEnd, uint40 revealEnd, uint40 exclusiveBlocks, uint24 reserveBps, uint24 maxBps, uint128 bond,
    /* new */ uint128 makerBond, address offerToken, uint128 minOffer, uint64 tlockRound);
event QueuedRoundOpened(address indexed maker, bytes32 indexed orderHash, address indexed opener, uint128 tip);
event RoundsEnqueued(address indexed maker, uint256 fromIndex, uint256 count);
event QueuedRoundWithdrawn(address indexed maker, uint256 index, bytes32 orderHash);
event BidCommitted(address indexed maker, bytes32 indexed orderHash, address indexed bidder, uint40 commitIdx,
    /* new */ bytes ciphertext);
event BidRevealed(address indexed maker, bytes32 indexed orderHash, address indexed bidder, uint24 bps,
    /* new, replaces the redundant `bond` (subgraph-design.md §10 item 8) */ address revealedBy);
event AuctionFilled(address indexed maker, bytes32 indexed orderHash, address indexed taker, uint256 amountIn, uint256 amountOut); // unchanged
event MakerDefaulted(address indexed maker, bytes32 indexed orderHash, uint8 reason, uint256 observed, uint256 required);
event AuctionSettled(address indexed maker, bytes32 indexed orderHash, address winner, uint24 clearingBps, bool winnerForfeited,
    /* new */ bool makerDefaulted);
event BondClaimed(address indexed maker, bytes32 indexed orderHash, address indexed bidder, uint128 amount); // unchanged
event ForfeitClaimed(address indexed maker, bytes32 indexed orderHash, /* new */ address indexed bidder, uint128 amount);
event UnrevealedForfeited(address indexed maker, bytes32 indexed orderHash, address indexed bidder, uint128 amount,
    /* new */ address recipient);
event MakerBondClaimed(address indexed maker, bytes32 indexed orderHash, address indexed to, uint128 amount, bool slashed);
```

`MakerDefaulted.reason`: `1` not shipped or docked, `2` declared balance below `minOffer`,
`3` wallet balance below `minOffer`, `4` allowance to Aqua below `minOffer`. First failure
wins; the check stops there.

`ForfeitClaimed` naming the bidder closes subgraph-design.md §10 item 5. `maker` and
`orderHash` stay indexed on every event so a room's whole history is two topics, as
today (`docs/design/LLD.md` §8).

### 3.7 Errors

Kept from v1, same selectors: `AlreadyOpened`, `NotOpened`, `BadWindow`, `CommitClosed`,
`RevealClosed`, `RevealNotOpen`, `AlreadyCommitted`, `NoCommitment`, `AlreadyRevealed`,
`BadReveal`, `BidOutOfRange(bps, reserveBps, maxBps)`, `NotRouter`, `NotSettled`,
`AlreadySettled`, `WindowNotElapsed`, `NothingToClaim`. `web/lib/bid.js:1260-1377` decodes
these by selector; the sentences carry over.

New:

| Error | Raised by | Condition |
|---|---|---|
| `NotMember()` | `open`, `enqueue`, `commit` | `inviteRoot != 0` and the proof does not verify for `msg.sender` |
| `NoEvidencePath()` | `open`, `enqueue` | `makerBond > 0` on a Book with `aqua == 0` |

bond backing an empty promise).

### 3.8 Invariants

Each is a Foundry invariant or a property asserted across the unit suite. The handler set
for the invariant runs is `open`/`enqueue`/`openNext`/`commit`/`reveal`/`revealFor`/
`postTransferIn` (pranked as the router)/`checkOffer`/`settle`/every claim, over a bounded
actor set and `vm.roll` steps.

- **I-1 Outcome is v1.** For any sequence of v1-shaped calls, `outcome()` on the v2 Book
  equals `outcome()` on a v1 Book driven identically. A differential test, not an
  argument: deploy both, drive both, compare per block.
- **I-2 Escrow conservation.** `tokenIn.balanceOf(book)` equals the sum over auctions of
  unclaimed bidder bonds plus unclaimed maker bonds, plus the sum over queues of
  `makerBond + tip` for unopened entries. Every claim path decrements exactly one term.
- **I-3 Every bond leaves once.** Per bid, `bondClaimed` flips at most once, via exactly
  one of `claimBond`, `claimForfeit`, `claimUnrevealed`. Per auction, `makerBondClaimed`
  flips at most once.
- **I-4 Phase disjointness.** No block admits both a reveal (`reveal` or `revealFor`) and
  a fill; no block admits both a fill and `settle`. Unchanged from
  `docs/design/LLD.md` §3, re-asserted with `revealFor` in the handler set.
- **I-5 Default needs evidence.** `makerDefaulted` is true only if some `checkOffer`
  call in `(revealEnd, revealEnd + exclusiveBlocks]` observed one of the four failures,
  and it never becomes true after the window. It never becomes true when `makerBond == 0`.
- **I-6 Slash direction.** `MakerBondClaimed.slashed == true` implies `to == best` and
  `makerDefaulted`; `slashed == false` implies `to == maker`. `winnerForfeited &&
  makerDefaulted` is unreachable (the first needs `filledBy != 0`, the second `== 0` at
  the time of the check, and `filledBy` is write-once).
- **I-7 Membership.** With `inviteRoot != 0`, every `AuctionOpened.maker` and every
  `BidCommitted.bidder` is a tree member. Fuzz over random trees.
- **I-8 Queue order.** `QueuedRoundOpened` events for one maker appear in `enqueue` order,
  each at `block.number >= notBefore`, each after the previous queued round's
  `AuctionSettled`.
- **I-9 Anyone-can-reveal changes nothing about the result.** For any set of reveals, the
  outcome is the same whether each reveal came from the bidder or from a third party, in
  any interleaving. Extends `testFuzz_TopTwo_MatchesReferenceScan`
  (`test/GlasshouseBook.t.sol:486-527`).
- **I-10 Router untouched.** `GlasshouseRouter` bytecode hash is identical before and
  after Phase 1. A one-line test against the artifact, so a "small" router change cannot
  ride along.

## 4. Timelock sealed bids: the facts, with sources

The proposal under evaluation: at commit the bidder posts the commitment hash *and* a drand
timelock ciphertext of `(bps, salt)` encrypted to a round at or after the end of the commit
phase; after that round anyone decrypts off chain and calls `revealFor`; the contract checks
the plaintext against the commitment exactly as today, so it needs no pairing and no
decryption. A bad ciphertext means nobody can reveal, which is the existing unrevealed-bond
forfeit. Evaluated below, not rubber-stamped. Verdict at §4.8.

### 4.1 drand quicknet

*Verified* on 2026-09-15 from `https://api.drand.sh/52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971/info`:

| Field | Value |
|---|---|
| chain hash | `52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971` |
| `period` | 3 s |
| `genesis_time` | 1692803367 |
| `schemeID` | `bls-unchained-g1-rfc9380` (signatures in G1, 48 bytes; public key in G2, 96 bytes) |
| public key | `83cf0f28…ece45a` (96 bytes) |
| `groupHash` | `f477d5c8…c5d3e` |

Round arithmetic, drand's own (`tlock` uses `network.RoundNumber(time)`, README
*verified*): `round(t) = floor((t - genesis) / period) + 1`, and round `r` is published at
`genesis + (r - 1) * period`. Checked against the live beacon: `/public/latest` returned
round `32226011` at wall clock `1789481397`, and `(1789481397 - 1692803367) / 3 + 1 =
32226011`.

"Unchained" matters: each round's signature is over the round number alone, so a
ciphertext to round `r` needs only round `r`'s signature to open, and `r` can be any
future round.

### 4.2 The trust, stated plainly

A drand round is a threshold BLS signature by the League of Entropy. The `tlock` README's
own sentence (*verified*): "if you trust there are never more than the threshold `t`
malicious nodes on the network you're relying on, you are guaranteed that your timelocked
data cannot be decrypted earlier than what you intended." The League's page says 15
member organisations (*verified*, `drand.love/loe`); the exact `t` for quicknet is in the
group file behind `groupHash` above and is *unverified* here - it must be read with
`drand show group` and written on the FAQ before this ships. Two failure modes, both to be
named on the page in the repo's voice:

- **`t` colluding operators can decrypt every sealed bid before the commit phase ends.**
  That is a return to open bidding, which is the shill-resistance loss described at
  `docs/design/HLD.md` §10.2, not a loss of funds.
- **`t` operators withholding, or an outage of the network, means nobody can decrypt in
  the reveal window.** Then every bidder must self-reveal (the v1 path, which stays). A
  bidder whose browser kept the salt (`web/lib/bid.js:987-1029` writes it before the
  wallet prompt) loses nothing; a bidder who trusted the timelock to do it and walked away
  loses the bond. The site must therefore keep storing the salt and keep the reveal button,
  and say: *anyone can open your bid for you; only you can guarantee it.*

drand has run since 2020 and quicknet since August 2023 (genesis above); that is a track
record, not a guarantee, and the doc should not dress it as one.

### 4.3 Mapping block numbers to drand rounds on Base

The Book keys every phase on `block.number` (`src/book/GlasshouseBook.sol:20-25`). The
timelock keys on wall-clock time. The bridge is Base's block timestamp, and it is exact
in one direction and only bounded in the other:

- **Block number to L2 timestamp is exact.** The OP Stack derivation spec requires
  `block.timestamp = prev_l2_timestamp + l2_block_time` with `l2_block_time` a chain
  constant, 2 s on Base, and empty blocks are produced to keep every slot filled
  (*verified*, `specs.optimism.io/protocol/derivation.html`). Probed live: four
  consecutive Base blocks, timestamps 8 s apart, on 2026-09-15. So at `open`, the
  timestamp of the first reveal block is `block.timestamp + 2 * (commitBlocks + 1)`,
  exactly.
- **L2 timestamp to wall clock is bounded above, not below.** The spec caps how far L2
  time may run *ahead* of its L1 origin (`max_sequencer_drift`), but nothing stops it
  falling *behind*: if the sequencer halts for ten minutes, the chain resumes by producing
  the backlog of 2 s slots quickly, each carrying the timestamp it was always going to
  carry. Block `commitEnd` then arrives on the wall clock later than its timestamp says.
  Measured drift on 2026-09-15 was seconds, not minutes.

Consequence for the choice of round. Let `T = timestamp(commitEnd + 1)` (exact) and pick
`tlockRound = round(T + M)` for a margin `M`. Then:

- if the chain runs on time, bids open `M` seconds into the reveal window and
  `revealBlocks * 2 - M` seconds remain for anyone to reveal;
- if the chain lags wall clock by `L` seconds during the commit phase, bids become
  decryptable `L - M` seconds before the commit phase closes on chain. For `L <= M` no
  leak. For a sequencer outage longer than `M`, sealed bids of that round are open before
  commits close, which is the shill-attack window again for one round.

So `M` trades reveal time against outage tolerance, and it is the maker's to set: the
maker passes `tlockRound` at `open` and the client checks it (§4.6). Defaults to write
into `config/auction.json`:

| Parameter set | reveal window | `M` | drand rounds of margin | time left to reveal |
|---|---|---|---|---|
| `humanDemo` 60/60/15 | 120 s | 30 s | 10 | 90 s |
| `advocated` 30/30/15 | 60 s | 12 s | 4 | 48 s |

Why the contract does not compute `tlockRound` itself: it could (`block.timestamp` is
available), but it would bake Base's 2 s cadence and drand's genesis into an immutable
contract. If either changes, every auction on the Book has a wrong round with no fix.
Recorded in the event, validated by clients, and the clients can be updated.

### 4.4 Ciphertext size and calldata cost

The IBE (Boneh-Franklin, the scheme `tlock` cites, *verified* README) ciphertext for the
G1-signature scheme is `U || V || W`:

- `U`: `r * G2generator`, a G2 point, 96 bytes compressed (public keys live in G2 for this
  scheme, so `U` does too);
- `V`: 32 bytes, `sigma XOR H2(e(H1(round), pk)^r)`;
- `W`: 32 bytes, `message XOR H4(sigma)`.

160 bytes, `TLOCK_CIPHERTEXT_LEN` in §3.4. The raw IBE encrypts at most one hash-length
message (32 bytes); `tlock` proper wraps an `age` file key and then encrypts the payload
with ChaCha20-Poly1305 (*verified* README), which is more than a 35-byte bid needs.
Glasshouse uses the raw IBE with a 32-byte plaintext: **the plaintext is the salt itself,
with `bps` carried in its top three bytes.** That is, `salt = bytes32(bps) << 232 | random
29 bytes`, the commitment stays `keccak256(bidder, bps, salt)` as at
`src/book/GlasshouseBook.sol:111-113`, and a decryptor recovers `bps` from `salt[0:3]`.
No contract change is needed for that; it is a client convention, and 29 random bytes is
232 bits of entropy, which is plenty for a commitment nobody can brute-force. The exact
domain-separation tags for `H2`, `H3`, `H4` must be copied from `drand/kyber`
`encrypt/ibe/ibe.go` and cross-checked against `tlock-js` (*unverified* here; §4.7 makes
it a test).

Cost of carrying 160 bytes in a `commit`:

- L2 execution: 160 non-zero calldata bytes at 16 gas is 2,560 gas; the `LOG` data is
  8 gas/byte, 1,280 gas, plus ABI padding. A v1 `commit` is about 90k gas, so this is a
  few percent.
- Storage: none. That is the point of the event-only choice: storing 160 bytes is five
  `SSTORE`s, about 100k gas, for data the contract never reads.
- L1 data: the bytes are random and do not compress, so Base's Fjord estimator charges
  for roughly the full 160 bytes. At 2026 Base fee levels that is a small fraction of a
  cent; measure it on the fork with the `GasPriceOracle` predeploy
  (`0x420000000000000000000000000000000000000F`, `getL1Fee(bytes)`) and print the figure
  in the Phase 1 log rather than trusting this sentence.

### 4.5 Is an event, not storage, enough?

Yes, for three reasons:

1. **The contract never needs the bytes.** Reveal is checked against the commitment
   (`src/book/GlasshouseBook.sol:192`); the ciphertext is only an off-chain aid.
2. **Logs are permanent chain data.** Every full node serves receipts for every block;
   the subgraph indexes `BidCommitted` and can store the bytes on the `Bid` entity (§6.3),
   so a reveal helper needs neither an archive node nor a log scan.
3. **Garbage costs the poster, not the venue.** A bidder who posts a ciphertext that does
   not open, or that opens to a plaintext that does not match their commitment, has made
   themselves unrevealable. That is exactly v1 silence, with the same consequence:
   `claimUnrevealed` (`src/book/GlasshouseBook.sol:329-342`). No new state, no new claim.

What storage would buy and does not: nothing. An on-chain copy could let the contract
*prove* a ciphertext was garbage, which it does not need to do because the forfeit already
fires on "unrevealed" regardless of why.

### 4.6 On-chain drand verification: EIP-2537 is live on Base, and not worth using here

*Verified* on 2026-09-15: an `eth_call` to `0x0b` (`BLS12_G1ADD`) on `mainnet.base.org`
with two points at infinity returned 128 zero bytes; an absent precompile would have
returned empty. `0x0f` (`BLS12_PAIRING_CHECK`) with empty input returned
`PrecompileError`, which is the specified behaviour for empty input (*verified*,
EIP-2537: "variable input length operations must return an error if the input is empty").
So the precompiles from Ethereum's Pectra are live on Base via the OP Stack Isthmus
upgrade. Gas (*verified*, EIP-2537): pairing check `32600*k + 37700`, `MAP_FP_TO_G1`
5,500, `G1ADD` 375; G1 points are 128 bytes uncompressed, G2 256.

What on-chain verification could do:

- **Prove a round has been published**, so the contract *knows* a reveal was possible.
  Cost: one 2-pair pairing check (about 103k gas) plus hash-to-G1 of the round id (two
  `MAP_FP_TO_G1` plus a `G1ADD` plus `expand_message_xmd` in Solidity, tens of thousands
  more) per proof. It would let the contract distinguish "nobody revealed because drand
  withheld" from "nobody revealed because the ciphertext was garbage". But the contract
  does not need to distinguish them: in the first case bidders self-reveal, in the second
  the forfeit is deserved, and in neither does the contract's decision change.
- **Decrypt on chain.** One pairing (`e(sig, U)`) plus hashes, then the commitment check.
  It removes nothing: the off-chain decryptor cannot lie, because the commitment check
  catches a wrong plaintext. It adds 100k+ gas to every reveal and 160 bytes of calldata
  again.

Verdict: do not add it. Note the option in the FAQ as available-but-pointless, with the
gas numbers, so a reader does not think it was overlooked.

### 4.7 The client side

`web/lib/tlock.ts` (plain ESM, imported by `bid.js`, the keeper and the tests): `encrypt(
round, plaintext32) -> 160 bytes`, `decrypt(signature48, ciphertext160) -> plaintext32`,
`roundAt(timestamp)`, `timeOfRound(round)`, `chainInfo` constants from §4.1 with the chain
hash pinned. Built on `@noble/curves` BLS12-381 (hash-to-curve per RFC 9380 with drand's
DST, pairing, G2 compression). Tests:

- round trip against fixed vectors produced by `tlock-js` or the `tle` CLI for the same
  round and message (the interop test; without it a domain-separation slip would produce
  ciphertexts only Glasshouse can open, which is worse than none);
- `roundAt` against the live value recorded in §4.1;
- a ciphertext to a past round decrypts immediately with that round's published
  signature (fetched once and checked in as a fixture);
- decrypting with the wrong round's signature fails the `U == H3(sigma||M) * G2` check.

Beacon sources: `api.drand.sh`, `api2.drand.sh`, `api3.drand.sh`,
`drand.cloudflare.com`, all serving the same chain hash; the client verifies the fetched
signature against the pinned public key before using it (one pairing in JS, cheap) so a
hostile mirror cannot feed a wrong signature - not that a wrong signature could do worse
than fail to decrypt.

### 4.8 Does anyone-can-reveal change the second-price incentives? What does the keeper do?

**Incentives.** In v1 a bidder decides whether to reveal *after* watching other reveals
land (`docs/design/LLD.md:906-912`), and the profitable deviation is the runner-up
staying silent to drop the winner's price to the reserve - bounded by the bond, not
removed. With a valid timelock ciphertext that decision no longer exists: from the
commit block on, the bid will be opened by whoever opens it first. The bidder's strategy
space collapses to what it is in the textbook: choose `bps`, or do not bid (a garbage
ciphertext is "do not bid" at the price of the bond, decided before any information).
Truthful bidding stays dominant under the same assumptions as before (`docs/design/HLD.md`
§10.1); what changes is that the mechanism now delivers the second price the theory
assumes, instead of a second price that a colluding runner-up could pull down. The maker's
blind shill at commit time (`README.md:147-152`) is unchanged and stays disclosed. Winning
still creates no obligation: a winner who does not fill keeps its bond unless someone else
fills (§3.10), exactly as now, so being revealed by a stranger costs a bidder nothing they
did not sign up for.

Two things that do change and are worth a sentence on the page: reveal order is now
decided by whoever is fastest to call `revealFor`, and it does not matter, because the
result is order-independent by construction (`docs/design/LLD.md` §2.4, I-9); and the
maker can open bids - also harmless, for the same reason, and only after `commitEnd`.

**The keeper.** After `commitEnd`, wait for `tlockRound` to be published (poll the beacon,
about `M` seconds), fetch every `BidCommitted` for the round from logs or the subgraph,
decrypt, and call `revealFor` for each bid not yet revealed, skipping any that fails to
decrypt or whose plaintext does not match the commitment (those are the bidder's problem
and the maker's forfeit). Then wait out the window, `checkOffer` once for its own round
(a self-check that also produces the event a verifier wants to see), `settle`, dock. The
reveal gas is the keeper's: the maker is the party that gains from every bid being
opened, so no tip is needed. The site offers the same action to any visitor as "open the
sealed bids" on a round page, for anyone who wants their own bid opened sooner than the
keeper gets to it.

## 5. `GlasshouseBookFactory` and rooms

```solidity
contract GlasshouseBookFactory {
    address public immutable aqua;                       // passed to every Book
    event RoomCreated(address indexed book, address indexed creator, bytes32 inviteRoot, string name);
    function create(bytes32 inviteRoot, string calldata name) external returns (address book);
    function count() external view returns (uint256);
    function roomAt(uint256 i) external view returns (address);
}
```

- `create` does `new GlasshouseBook(inviteRoot, aqua)` (plain `CREATE`; deterministic
  addresses buy nothing because the subgraph template follows the event), appends to
  `rooms[]`, emits. `name` is bounded (`<= 64` bytes) and lives only in the event; the
  Book has no name storage and no owner. The creator is not stored on the Book either:
  membership is the root, and the creator is just the address that paid.
- The **public v2 room** is `create(bytes32(0), "Glasshouse")`, called once at deploy.
  Its Book is the one the keeper, the site's front page and `config/rounds.json` v2 point
  at. There is deliberately no "special" Book: the public room is room 0.
- The factory has no admin either. Its `aqua` is immutable because every Book on a chain
  wants the same one.
- Cost: one Book deployment per room, about 10-13 KB of init code. On Base that is cents
  at 2026 gas prices; the create flow prints the estimate before the wallet prompt.

Why not a `roomId` in one Book or a UI filter: `README.md:469-486` already argues it and
nothing here changes the argument. Separate storage, separate escrow, a bug in one room
cannot reach another, and "invite-only" is a property of a contract, not of a page.

The size guard already covers the factory (§2). The Ignition module gains
`GlasshouseBookFactory(aqua)` and a `create(0, "Glasshouse")` call, and records the public
room's address in `deployed_addresses.json` like the v1 Book.

`subgraph/src/helpers.ts:33-35` both grow a `book` argument. Every handler that today

### 6.3 Mapping

`src/book-v2.ts` is `src/book.ts` with: the id change; `handleBidCommitted` storing the

## 7. The site

Principles from `web/` carry over: the chain for the live card, the subgraph for
history, every figure named, honest empty states, the provenance lint.

- **`/rooms`**: list from the subgraph (`rooms(orderBy: createdAtBlock)`), each with name,
  public/invite-only chip, auction count, last activity. Chain fallback: `RoomCreated`
  logs from the factory (one topic, chunked like `scripts/verify-run.mjs:79-104`), so the
  page works with the subgraph off.
- **`/rooms/new`**: name, a textarea of addresses, an optional maker bond default. Builds
  the `StandardMerkleTree`, shows the root and the cost estimate, sends `create`. The full
  address list is what proofs are made from, so the page offers it as a download and
  writes it to `localStorage` under `glasshouse:room:<root>`; the room page says plainly
  that whoever holds the list can make invites, and that the list is not on chain. Invite
  link: `/rooms/<book>?p=<proof hex>`; the proof is that address's and is rejected for any
  other, so a leaked link is useless to a stranger.
- **`/rooms/<book>`**: the room-scoped board. `useAuctions` takes `book` (today a constant,
  `web/lib/useAuctions.ts:142`); for rooms with no rounds manifest the auction list comes
  from the subgraph and `chain.js` reads each listed auction live
  (`web/lib/chain.js:288-334` already takes `book`; `newestOpenedRound`'s binary search
  over the manifest, `web/lib/chain.js:259-282`, stays for the public room only).
  `bid.js` already has `configure({ book })` (`web/lib/bid.js:56-60`); the room page calls
  it, and `placeBid`/`openRound` pass the proof from the URL.
- **Sealing with a timelock.** `placeBid` step 1 (`web/lib/bid.js:975-976`) becomes:
  generate 29 random bytes, form the 32-byte plaintext with `bps` in the top three bytes,
  encrypt to the round's `tlockRound`, and refuse to commit if
  `timeOfRound(tlockRound) < timestamp(commitEnd + 1)` or `> timestamp(revealEnd) - 10 s`
  (the client-side validation of §4.3), or if the chain's head timestamp lags the wall
  clock by more than the margin. The salt is still written to `localStorage` before the
  wallet prompt, exactly as now (`web/lib/bid.js:987-1029`); the sentence on the card
  changes from *reveal in the window or lose the bond* to *anyone can open this bid after
  block N; you can still open it yourself.*
- **Open the sealed bids.** On a round page after `commitEnd`, when `tlockRound`'s beacon
  is published: fetch, decrypt every unrevealed `BidCommitted` ciphertext, and offer one
  `revealFor` per bid (or a batched call through a tiny multicall if Phase 1 adds
  `revealForMany`; recommended, it is a loop over `revealFor`).
- **The maker bond on the receipt.** Where the receipt says "no fill reported to the
  Book", it now also says whether the offer was checked, what it observed, and where the
  maker bond went. A round with `makerBond == 0` says "unbonded maker", not nothing.
- **Open a round** (`web/components/OpenRound.tsx`): gains the three offer fields, the
  timelock toggle (on by default), and the sentence that a browser-opened round with no
  shipped order cannot carry a maker bond, because `NotShipped` would refuse it - the
  contract's refusal is the page's explanation.

`web/lib/bid.js` and `web/lib/chain.js` to TypeScript (`README.md:453-458`,
`TODO.md:53-57`) is not a v2 feature but every item above touches those files; §11 puts
it in parallel, before Phase 6 lands.

### 8.1 Keeper

  (default 0). Then loop: `openNext` when due (unless someone else did), house commit with

  dock, `claimBond`, `claimMakerBond`. State file semantics unchanged (salt written before

  fixed here and is noted.
- `DRY_RUN=1` still refuses a non-fork node (`scripts/keeper.ts:172-180`).

### 8.2 `verify-run.mjs`

Today it reads one address (`scripts/verify-run.mjs:37, :91`) and keys auctions by
`maker + orderHash` (`scripts/verify-run.mjs:116-118`). Changes: `--factory <addr>`
discovers rooms from `RoomCreated` logs (plus `--book` repeated for the legacy Book), scans
each Book's logs, keys by `book + maker + orderHash`, decodes both ABIs by address. New
checks, each with the three-valued `n/a` rule (`scripts/verify-run.mjs:53-66`):

- `ROOMS`: every `RoomCreated` book has code and its `inviteRoot()` matches the event;
- `REVEALED_BY`: every `BidRevealed` with `revealedBy != bidder` is on a round whose
  `AuctionOpened.tlockRound != 0` and whose `BidCommitted` carried a ciphertext. The
  verifier cannot re-derive the commitment (the salt is not in any event), so this is the
  weaker check the chain allows: the contract accepted the reveal, and the bid was sealed
  with a timelock. Said as such in the check's detail line;
- `MAKER_BOND`: for every round with `makerBond > 0`, `MakerBondClaimed` went to the
  winner iff `MakerDefaulted` was emitted, and never both a slash and a `ForfeitClaimed`;
- `QUEUE`: `QueuedRoundOpened` blocks are `>= notBefore` (read from `RoundsEnqueued` and
  the queue view) and after the previous round's settle.

`rebuild()` stays the one independent derivation and is still what `cross-check` imports.

## 10. Findings from reading the code for this design

Recorded whether or not v2 acts on them.

- **F-v2-1. A hook-bearing order is not fillable until its auction opens.** `README.md:327-329`
  says an order carrying the gate with no auction open "stays fillable as a plain limit
  order". True for the gate (`src/lib/GlasshouseAuctionLib.sol:54`; `test/GlasshouseVM.t.sol:196-203`,
  which builds the order with `withFillHook = false`), false for the whole order once the
  hook is set: `postTransferIn` reverts `NotRouter()` while `a.router == 0`
  (`src/book/GlasshouseBook.sol:251`), and `SwapVM` does not catch hook reverts
  (`node_modules/@1inch/swap-vm/src/SwapVM.sol:298-301`). Every keeper round sets the hook.
  For v2 this is the property that makes a pre-shipped queue safe (§3.2); for the README
  it is a sentence to narrow to "an order without the fill hook". No v1 behaviour changes.
- **F-v2-2. `Protocol` is keyed by Book address** (`subgraph/src/helpers.ts:72-74`), so the
  template design would silently create one Protocol per room. Fixed by §6.2, not a bug in
  v1 with one Book.
- **F-v2-3. `Auction.id` collides across Books.** `key(maker, orderHash)` is unique per
  Book, not per chain (`src/book/GlasshouseBook.sol:102-104`), and the same shipped order
  can be auctioned once per Book. §6.2 prefixes the Book address.
- **F-v2-4. `BidRevealed.bond` is redundant** (`docs/design/subgraph-design.md` §10 item 8);
  v2 replaces it with `revealedBy` rather than growing the event.
- **F-v2-5. The maker bond needs `tokenIn` allowance to the Book from the maker**, a third
  spender after Aqua and the Book-for-bidder-bonds the keeper already handles
  (`scripts/keeper.ts:239-254`). Same address as the bidder-bond spender, so one approval
  covers both; noted so the keeper's approve step is sized for `K * (makerBond + tip)`.
- **F-v2-6. `TEAM_ADDRESSES` still lists only the maker** (`subgraph/src/provenance.ts:19`;
  `TODO.md:32-40`). The v2 subgraph republish is the moment to add the live-fill bidders.

## 12. Decisions that need the user

Recommendations given; none of these should be decided by an implementation agent.

| # | Decision | Recommendation |
|---|---|---|
| D-v2-1 | Invite root per Book (immutable, a new list means a new room) or per auction (set at `open`)? | **Per Book.** It is the README's design, one slot, and rooms stay cheap. Per-auction adds a slot per auction and makes "which list am I on" a per-round question. |
| D-v2-2 | Does the root gate `open`/`enqueue` as well as `commit`? | **Yes.** A room is a membership set; a public opener with a private bidder list is a different product. |
| D-v2-3 | When the maker defaulted, do unrevealed-bidder forfeits go to the winner or still to the maker? | **To the winner.** A maker must not profit from a round it broke. The cost is one conditional recipient. |
| D-v2-4 | Is a maker default sticky once flagged in the window? | **Yes.** Otherwise the check is a race the maker can always win by watching. |
| D-v2-5 | `settle()` opens the next round, or `openNext` with a tip, or both? | **`openNext` + tip, plus a `settleAndOpenNext` convenience; `settle` itself unchanged.** §3.2 gives the three reasons. |
| D-v2-6 | Timelock per auction (maker chooses at `open`) or mandatory on the Book? | **Per auction, on by default in every client.** A Book-level mandate would refuse a maker who cannot reach drand; the per-auction flag records the choice in the event where a reader can see it. |
| D-v2-7 | Maker bond denominated in `tokenIn` (one escrow token per auction) or in `offerToken`? | **`tokenIn`.** One `SafeERC20` path, one approval for the maker, and forfeits reach the winner in the token they were bidding with. |
| D-v2-8 | On-chain drand signature verification via EIP-2537? | **No.** §4.6: live on Base, costs about 100k gas per proof, and changes no decision the contract makes. Record the option in the FAQ. |
| D-v2-9 | The v1 Book indexed as a legacy room in the v2 subgraph? | **Yes.** `/evidence` keeps its history and the mainnet fill; the cost is a second static source and a second ABI. |
| D-v2-10 | The TypeScript migration (W0) before Phase 6? | **Yes, in parallel from the start.** Doing Phase 6 in JavaScript and migrating afterwards is the same diff twice. |
| D-v2-11 | Mainnet deploy trigger. | **Only after reading the fork rehearsal log, and only by explicit instruction.** Phases 1-7 are all buildable and testable against a fork; nothing is lost by waiting. |
| D-v2-12 | Batch size `K` and the house `makerBond`/`tip` defaults for the public room. | `K = 12`, `makerBond` sized to about three rounds of a bidder's gas at Base prices, `tip = 0` while the house keeper runs and a small non-zero tip once it is meant to run unattended. Numbers to be written into `config/auction.json` with their basis, like the existing ones. |

Two facts still marked *unverified* above and to be settled before the FAQ is written:
quicknet's exact threshold `t` (`drand show group`, §4.2), and the IBE domain-separation
tags (the Phase 3 interop test, §4.4).
